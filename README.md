# Avito: рекомендация услуг по поисковому запросу

## Задача

Дано три parquet-файла (каталог `dataset_extract/` рядом с этой папкой):

- `train.parquet` — 497 673 пары «запрос → кликнутое объявление» на платформе Авито Услуги;
- `benchmark_queries.parquet` — 2 452 поисковых запроса;
- `benchmark_items.parquet` — 189 212 объявлений (корпус-кандидат), включая название, описание, параметры услуги, микрокатегорию, локацию, рейтинг продавца.

Для каждого запроса из бенчмарка нужно вернуть до 50 объявлений из корпуса. Релевантное объявление = то, по которому у этого запроса были клики в train.

Метрика — `Recall@50`: доля релевантных объявлений запроса, попавших в топ-50 ответа. Между разными запросами метрика усредняется.

Правила сдачи:
- инференс без внешних API (все модели локальные, заранее обученные/скачанные);
- файл `answer.csv` с колонками `query_id`, `answer`;
- `item_id` — 16-символьный hex в нижнем регистре, не более 50 уникальных на строку, через пробел;
- запись без индекса (`to_csv(index=False)`), итого 2 452 строки + заголовок;
- даётся 7 попыток сдачи.

Формат ответа:
```
query_id,answer
70DfDUpwjxB4lzFd,d01e14d2ffd4ddba 14d535285758af89 ... (до 50 id)
```
⚠️ Любая строка, нарушающая формат (лишний столбец, не-16-hex id, дубликаты внутри строки, больше 50 позиций), может обнулить ответ.

## Что внутри решения

Подход — каскад кандидатов из независимых каналов поиска + линейная фьюжн-модель: балл объявления = скалярное произведение вектора признаков (0..1 на канал) на веса, подобранные на валидации.

Каналы (по каждому храним топ-4000 кандидатов на запрос):

1. **BM25 по полному тексту** (название + описание + параметры). Стемы pymorphy2, sparse-матрица, ранжирование по краткой формуле BM25 с k1=1.5, b=0.75.
2. **BM25 по заголовку** (k1=1.3, b=0.5) — для коротких запросов заголовок информативнее полного текста.
3. **Dense** — косинусная близость эмбеддингов rubert-tiny2 (312-мерные) между запросом и объявлением.
4. **Transfer** — клики похожих train-запросов: берём топ-90 ближайших по эмбеддингу запросов из train (порог похожести 0.3) и собираем их кликнутые объявления.
5. **Exact** — клики по точно такому же тексту запроса, если он есть в train.
6. **Microcat** — микрокатегории кликнутых товаров похожих запросов; товары корпуса из этих категорий.
7. **Title-all** — объявления с ВСЕМЯ словами запроса в заголовке (жёсткое условие поверх школьного BM25).
8. **Pop** — самые кликаемые товары корпуса (страховка на случай полного несовпадения словаря).

Построение матрицы признаков: значения каналов приводятся к «1 − ранг/длина», чтобы каналы были сопоставимы; к 7 базовым признакам добавляются 3 бинарных: точное совпадение запроса, совпадение локации поиска с локацией объявления, фильтр «рейтинг ≥ 4» (эти сигналы из exploration: 83% кликов совпадают по локации; рейтинг — явный фильтр в тексте запроса).

Выбор топ-50 — по сумме взвешенных признаков через `argpartition` (без полной сортировки).

**Веса у запросов разные — по принадлежности текста запроса к train.** Бенчмарк на ~63% состоит из запросов, которых нет в train, и на ~37% — из тех, что есть (совпадение по нормализованному тексту; по факту 918 из 2452). У них разные оптимальные стратегии:

- `out/best_weights.npy` (fresh, для 1534 новых запросов) — подобраны на отложенных 1600 запросах train с выключенной утечкой: свои клики запроса недоступны, как и у настоящих свежих запросов. Тонкий координатный спуск (шаги 0.1 → 0.05 → 0.02): `[2.2, 0.02, 0, 0.22, 0, 0.57, 0.25, 3.0, 0.6, 0.4]`, честный R@50 = 0.5701.
- `out/best_weights_overlap.npy` (для 918 запросов, чей текст есть в train) — подобраны на тех же отложенных запросах, но с включённой утечкой: здесь свой клик в train — это и есть правильный сигнал, а не утечка. Канал exact один даёт 0.995, поэтому инъекция: `[2.2, 0, 0, 0.3, 0, 0.4, 0.25, 3.0, 0.6, 0.4]`.

В `predict.py` веса выбираются строкой: `query_id` в множестве `train_queries.parquet n_q` → overlap-веса, иначе fresh. Проверено на бенчмарке: при переходе от единых весов к раздельным 0 из 918 overlap-строк не изменились (регресс на сильной группе невозможен), fresh пересчитаны полностью.

Решение о точках, по которым стоили подбора:

- **Анти-утечка в валидации была обязательна.** Валидационные запросы исключаются из transfer-канала, обнуляются их строки в матрице микрокатегорий и пересчитывается популярность без их кликов. Без этого локальный Recall завышался (0.624 вместо честных 0.566) и подбирались перекошенные веса.
- **Dense в соло почти бесполезен** (R@50 ≈ 0.05) и на чистой валидации его вес сходится к нулю: для пересечений train/бенчмарк важнее exact/transfer; для свежих запросов надежду даёт BM25. Оставлять его вес намеренно большим в ущерб валидации не стали — честная валидация в приоритете.
- **Microcat в соло = 0** — кликнутые товары слабо повторяют микрокатегории похожих запросов; канал оставлен только через передаваемый через фьюжн сигнал.

Честный Val R@50 (fresh-веса, после тонкого подбора) = **0.5701**. Прокси-оценка на пересечениях: 91 запрос бенчмарка, совпадающий с train по тексту и имеющий клики в корпусе → query-hit@50 = 0.945, recall по товарам = 0.747. Ожидаемый балл бенчмарка — на уровне 0.7 (локальная валидация занижает: бенчмарк на две трети состоит из «свежих» запросов, а overlap-группа почти насыщена каналом exact).

## Состав проекта

| Файл | Назначение |
|---|---|
| `config.py` | пути `HERE/CACHE/OUT/BASE`, вычисляются относительно расположения файлов — папку можно переносить, рядом должна лежать `dataset_extract/` |
| `prep.py` | нормализация, стемминг, sparse-матрицы BM25, кэши |
| `embeddings.py` | эмбеддинги rubert-tiny2 для объявлений и уникальных запросов |
| `retrieval.py` | BM25, каналы кандидатов, построение признаковой матрицы; `Retriever` общий для валидации и инференса |
| `validate.py` | отложенная выборка 1600 запросов, режимы `fresh` (анти-утечка) и `overlap` (утечка включена — имитация запросов, чей текст есть в train), соло-оценки, тонкий подбор весов → `out/best_weights.npy`, `out/best_weights_overlap.npy` |
| `predict.py` | инференс на бенчмарке; вес выбирается строкой по принадлежности запроса к train → `out/answer.csv` |
| `cache/` | промежуточные артефакты, пересобираются скриптами |
| `out/` | `answer.csv` (ответ), `best_weights.npy`, кэши валидации и бенчмарка |

Ключевые кэши: `train_queries.parquet` — 73 737 уникальных нормализованных запросов train (порядок совпадает со строками `train_q_emb.npy` и матрицы микрокатегорий); `item_emb.npy` 189 212×312; `full_mat.npz`/`title_mat.npz` — разреженные матрицы «документ × стем».

## Запуск

Требования: Windows/CPython 3.11, ~8 ГБ RAM (вал считать по одному запросу за раз). Зависимости: `pandas`, `numpy`, `scipy`, `sklearn`, `pymorphy2`, `torch`, `sentence-transformers`.

```
python prep.py          # этап 1: предобработка, BM25-матрицы
python embeddings.py    # этап 2: эмбеддинги (первый запуск скачивает rubert-tiny2 — нужен интернет)
python validate.py overlap   # шаг 3а: overlap-фичи и веса (запросы, чей текст есть в train)
python validate.py      # шаг 3б: fresh-фичи и веса; если overlap-фичи уже построены — и их тоже
python predict.py       # этап 4: answer.csv (из кэша кандидатов ~2 мин)
```

Порядок критичен: `validate.py` и `predict.py` читают кэши предыдущих этапов. Если удалён `out/val_feats.pkl` или `out/val_feats_overlap.pkl`, соответствующий режим валидации перестроит признаки (займёт заметно дольше). Если удалён `out/bench_retrieval.pkl`, `predict.py` перестроит кандидаты бенчмарка (это тяжёлый шаг).

`embeddings.py` и `predict.py` повторные запуски идемпотентны — перезаписывают те же файлы.
